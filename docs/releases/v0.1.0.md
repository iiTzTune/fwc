# Field Wireless Companion v0.1.0

This release ships the local observation dashboard, a channel-cycling capture
worker, and a plugin host with per-plugin process budgets. The Rust core
supervises services and stores acknowledged events in SQLite. The flash image
uses two OS slots and a separate writable volume for configuration and activity
records.

## Download and verify

`fwc-x86_64.img.zst` contains the full disk image for 64-bit UEFI. Use it for
a fresh installation. `fwc-slot.ext4.zst` contains one OS slot for an existing
device. Both artifacts are covered by the signed `SHA256SUMS` manifest.
The release signing identity is `fwc-release`; verify its public key fingerprint
with a trusted copy before checking signatures.

```text
SHA256:Fuv3LdOFYESNny6xWVxg4w8P9KfqZSOl9selZPkfKVM
```

From a new download directory with GitHub CLI, OpenSSH, zstd and sha256sum,
fetch the release assets. Check the fingerprint of the key in the allowed
signers file and verify the checksum manifest before opening either image.

```sh
gh release download v0.1.0 --repo iiTzTune/fwc
awk '{print $3, $4}' release-signers | ssh-keygen -lf -
ssh-keygen -Y verify -f release-signers -I fwc-release -n fwc-image -s SHA256SUMS.sig < SHA256SUMS
sha256sum --check --ignore-missing SHA256SUMS
zstd -dk fwc-x86_64.img.zst fwc-slot.ext4.zst
sha256sum --check SHA256SUMS
```

To verify the signed source tag, use the same trusted signer file in a
checkout of the project.

```sh
git fetch origin tag v0.1.0
git -c gpg.format=ssh -c gpg.ssh.allowedSignersFile="$PWD/docs/release-signers" verify-tag v0.1.0
```

Follow the [bring-up guide](https://github.com/iiTzTune/fwc/blob/v0.1.0/docs/bringup.md)
for flash and first-boot instructions. For an installed device, use the
decompressed slot image and the digest for `fwc-slot.ext4` when staging an
update. [Update procedure](https://github.com/iiTzTune/fwc/blob/v0.1.0/image/UPDATE.md)

## Device support

The image targets the UP Board x5-Z8350 with 64-bit UEFI. QEMU verification
covers startup, persistent identity, the local API, and rollback from a failed
trial. Board boot, USB radio operation on that board, panel refresh, physical
button input, battery readings and watchdog reset remain on the hardware
checklist. The Waveshare 2.13in V4 backend requires compatible SPI/GPIO
transport. [Hardware evidence ledger](https://github.com/iiTzTune/fwc/blob/v0.1.0/docs/bringup-checklist.md)

The raw disk and slot digests match the clean local build and both independent
GitHub-hosted image builds. Each hosted image reached the live API twice and
retained its first-boot device identity.
